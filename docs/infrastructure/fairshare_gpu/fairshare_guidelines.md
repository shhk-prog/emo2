# GPUタイプ別 FairShare コスト最適化ガイドライン

## 1. 背景と計算式概要

FairShareのポイント消費式は、利用するGPUタイプ（ノード/パーティション）に応じて以下の計算式が適用されます。

$$\text{Cost} = (\text{GPU係数} \times \text{GPU枚数} + \text{CPUコア数}) \times \text{利用時間(秒)}$$

### GPUタイプ別の比較一覧

| GPUタイプ | GPU係数 ($W_{GPU}$) | CPU=1, GPU=1時の毎秒コスト | 相対コスト (vs a6000) | VRAM容量 | 主な特徴と推奨用途 |
| :--- | :---: | :---: | :---: | :---: | :--- |
| **a6000** | **15** | 16 pt/s | **1.00x** | 48 GB | **最安コスト**。7B〜13Bモデルの標準的な推論・評価ジョブに最適 |
| **h100** | **30** | 31 pt/s | **1.94x** | 80 GB | **高スループット**。FP8推論、大バッチ処理、または高速化が必須なタスク |
| **a6000-ada** | **30** | 31 pt/s | **1.94x** | 48 GB | 高速画像生成・描画、またはAdaアーキテクチャ最適化タスク |
| **h200** | **40** | 41 pt/s | **2.56x** | 141 GB | **超大容量VRAM**。70Bクラスの単一GPU推論、超長文コンテキスト(32k+) |
| **all (未指定)** | **45** | 46 pt/s | **2.88x** | - | **ペナルティ**。パーティション未指定時に適用。**使用厳禁** |

---

## 2. 最適化のための 4 つの鉄則

### 鉄則 1: ジョブ投入時にGPUタイプ/パーティションを明示する (ペナルティ回避)
- パーティション指定を省略して `all`（係数 45）が適用されると、a6000 (15) の **2.88倍**、H100 (30) の **1.48倍** のポイントを浪費します。
- Slurmスクリプトには必ず `--partition=<gpu_type>` または `--gres=gpu:<gpu_type>:1` を明示してください。

### 鉄則 2: CPUコア数は原則 1〜2 コアに最小化する
- コスト式に `CPUコア数` がそのまま加算されるため、CPU確保の比重が大きくなります。
- **例 (a6000の場合)**:
  - CPU 1コア: $15 \times 1 + 1 = 16$ pt/s
  - CPU 16コア: $15 \times 1 + 16 = 31$ pt/s (**コストが約2倍に膨らみ、H100と同等になる**)
- データロード等でボトルネックにならない限り、`--cpus-per-task=1` または `2` に留めてください。

### 鉄則 3: 単一GPUでのバッチサイズ最大化 (OOM限界攻め)
- Multi-GPU (Tensor Parallelismなど) を使うとGPU係数が倍増します（例: H100 2枚 = $30 \times 2 + 1 = 61$ pt/s）。
- 処理時間が半分（50%削減）以下にならない限り、マルチGPU化は総コストを増加させます。
- **原則**: 1枚のGPUメモリに収まるモデルであれば、**1 GPUで `batch_size` や `gpu_memory_utilization` を極限まで高める**のが最もコスト効率が良いです。

### 鉄則 4: 70Bクラスモデルは H100 2枚 ではなく H200 1枚 を選ぶ
- **H100 2枚 (TP=2)**: コスト係数 $30 \times 2 + 1 = 61$ pt/s
- **H200 1枚 (TP=1)**: コスト係数 $40 \times 1 + 1 = 41$ pt/s (VRAM 141GBで70Bモデルが1枚に載る)
- H200 1枚にまとめることで、**ポイント消費量を約33%削減**でき、さらにTensor Parallelismの通信オーバーヘッドも解消できます。

```
[タスク発生]
   │
   ├─► Q1. モデルサイズは？
   │    │
   │    ├─► 7B 〜 13B クラス (VRAM < 48GB)
   │    │    │
   │    │    ├─► Q2. 処理速度 (秒間スループット) の緊急度は？
   │    │    │    ├─► 通常・バッチ処理 ──► 【a6000】 (最安)
   │    │    │    └─► 最高速・リアルタイム性重視 ──► 【h100】 (FP8活用)
   │    │
   │    └─► 70B 以上 / 超長文コンテキスト (VRAM > 48GB)
   │         │

   │         └─► VRAM 141GB超 ──► 【h200 2枚】 または 【h100 Multi-GPU】
```

## 4. コスト・速度のトレードオフ計算 (損益分岐点)

### a6000 vs H100 の損益分岐点
- a6000 コスト係数 = 16 (CPU=1)
- H100 コスト係数 = 31 (CPU=1)
- **判定基準**: H100 での処理時間が a6000 の **$\frac{16}{31} \approx 51.6\%$ 以下**（つまり **1.94倍以上高速**）になれば、H100 の方が安くなります。
  - **通常推論**: a6000 でも十分なバッチを積める場合は **a6000 が優勢**。
  - **FP8推論 / 大規模vLLM**: H100 の Transformer Engine により 2.5 倍以上高速化する場合は **H100 が優勢**。

## 5. 推奨 Slurm 設定例

### A. 7B/13Bモデルの通常評価・大量バッチ処理 (最安構成)
```bash
#!/bin/bash
#SBATCH --job-name=eval_7b_a6000
#SBATCH --partition=a6000
#SBATCH --gres=gpu:a6000:1
#SBATCH --cpus-per-task=1
#SBATCH --time=02:00:00

# vLLMの設定例: バッチサイズ最大化 + VRAM活用率90%
python3 benchmark_vllm.py \
    --model Qwen/Qwen2.5-7B-Instruct \
    --batch-size 512 \
    --gpu-memory-utilization 0.90 \
    --cpu-cores 1
```

### B. 70Bモデルの高品質・大容量推論 (H200 1枚構成)
```bash
#!/bin/bash
#SBATCH --job-name=eval_70b_h200
#SBATCH --partition=h200
#SBATCH --gres=gpu:h200:1
#SBATCH --cpus-per-task=2
#SBATCH --time=01:00:00

# 141GB VRAMを活かして70Bモデルを単一GPUで駆動
python3 benchmark_vllm.py \
    --model meta-llama/Llama-3.1-70B-Instruct \
    --batch-size 128 \
    --gpu-memory-utilization 0.92 \
    --cpu-cores 2
```
